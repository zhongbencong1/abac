# ABAC 鉴权系统 — 操作流程说明

本文档说明本系统的推荐操作顺序、各功能用法及鉴权逻辑，便于首次使用或培训他人。

---

## 一、系统概览

本系统实现**基于属性的访问控制（ABAC）**：根据**主体（谁）**、**资源（对什么）**、**操作（做什么）**及可选**环境**的属性，通过**策略规则**判断是否允许访问。无匹配策略时默认**拒绝**。

| 概念     | 说明                     | 在本系统中的维护入口   |
|----------|--------------------------|------------------------|
| 主体     | 发起访问的用户/角色等    | 用户管理（主体属性）   |
| 资源     | 被访问的对象            | 鉴权时传入 JSON        |
| 操作     | read / write / delete 等 | 鉴权时传入             |
| 环境     | 时间、IP 等可选上下文    | 鉴权时传入 JSON        |
| 策略     | 规则集合 + 允许/拒绝效果 | 策略配置               |
| 属性定义 | 规则中可引用的属性名     | 属性管理（可选，作规范）|

---

## 二、推荐操作流程（首次使用）

### 步骤 1：启动服务

1. **启动后端**（在项目 `backend` 目录下执行）  
   ```bash
   mvn spring-boot:run
   ```  
   看到 `Started AbacApplication` 即表示成功，服务地址：`http://localhost:8080`。

2. **启动前端**（在项目 `frontend` 目录下执行）  
   ```bash
   npm install   # 仅首次需要
   npm run dev
   ```  
   浏览器访问控制台给出的地址（如 `http://localhost:5173` 或 `http://localhost:5175`）。

---

### 步骤 2：用户管理 — 维护“谁”在做鉴权

**入口**：左侧菜单 **「用户管理」**。

- **作用**：为每个用户维护其**主体属性**。鉴权时若选择“按用户加载主体”，系统会用该用户的主体属性作为 `subject`。
- **操作**：
  - 点击 **「新增用户」**。
  - **用户名**：必填，唯一，如 `admin`、`zhangsan`。
  - **显示名**：可选，如“管理员”、“张三”。
  - **主体属性 (JSON)**：必填，一个 JSON 对象，描述该用户具备的主体属性。  
    示例：`{"role":"admin","department":"IT"}` 表示该用户 `role=admin`、`department=IT`。  
    策略里若写了 `subject.role`、`subject.department`，就会和这里的键值对应。
- **说明**：主体属性键名建议与「策略配置」里用到的 `subject.xxx` 一致（`xxx` 即键名）。

---

### 步骤 3：属性管理 — 定义可用的属性（可选但推荐）

**入口**：左侧菜单 **「属性管理」**。

- **作用**：统一维护主体/资源/环境属性的**名称、分类、值类型**，便于在「策略配置」里按名称选择，并保持命名一致。
- **操作**：
  - 点击 **「新增属性」**。
  - **属性名**：如 `role`、`department`、`type`、`sensitivity`。
  - **分类**：**主体 (subject)** / **资源 (resource)** / **环境 (environment)**。
  - **值类型**：字符串 / 数字 / 布尔。
  - **说明**：可选备注。
- **示例**：  
  - 主体属性：`role`（subject）、`department`（subject）。  
  - 资源属性：`type`（resource）、`sensitivity`（resource）。

---

### 步骤 4：策略配置 — 定义允许/拒绝规则

**入口**：左侧菜单 **「策略配置」**。

- **作用**：配置若干条**策略**。每条策略由多条件组成（逻辑与），满足则按该策略的**效果**返回允许或拒绝。按**优先级**从小到大匹配，先匹配到的策略生效。
- **操作**：
  - 点击 **「新增策略」**。
  - **策略名**：如“管理员可访问报表”。
  - **效果**：**允许** 或 **拒绝**。
  - **优先级**：数字越小越先匹配，如 `10` 比 `100` 优先。
  - **启用**：勾选后该策略才参与鉴权。
  - **规则表达式**：  
    - 可用界面上的**可视化条件**：选择属性（如 `subject.role`）、操作符（如 等于、属于）、值。  
    - 或直接编辑下方 **JSON**。格式为数组，每项一条条件，例如：  
      ```json
      [
        { "attribute": "subject.role", "op": "eq", "value": "admin" },
        { "attribute": "resource.type", "op": "eq", "value": "report" }
      ]
      ```
- **操作符**：`eq`（等于）、`neq`（不等于）、`in`（属于列表）、`not_in`、`gt`/`gte`/`lt`/`lte`（大小比较）、`exists`/`not_exists`（存在/不存在）。

---

### 步骤 5：鉴权校验 — 发起一次鉴权并查看结果

**入口**：左侧菜单 **「鉴权校验」**。

- **作用**：模拟一次访问请求，根据当前配置的**用户与策略**得到**允许/拒绝**及匹配的策略名；结果会写入**审计日志**。
- **操作**：
  1. **按用户加载主体**（可选）：在「按用户加载主体」下拉框中选择已创建的用户，系统会将该用户的**主体属性**填入下方「主体属性 (subject)」文本框。
  2. **操作 (action)**：填写本次操作，如 `read`、`write`、`delete`。
  3. **主体属性 (subject)**：若未选用户，可手填 JSON，如 `{"role":"admin","department":"IT"}`。与用户管理中的主体属性格式一致。
  4. **资源属性 (resource)**：填写被访问资源的属性，如 `{"type":"report","sensitivity":"low"}`。
  5. **环境属性 (environment)**：可选，如 `{}` 或 `{"ip":"192.168.1.1"}`。
  6. 点击 **「发起鉴权」**。
- **结果**：页面会显示本次鉴权是否**允许**、**原因**（如匹配到的策略名），以及若无匹配则“No matching policy (default deny)”。

---

### 步骤 6：审计日志 — 查看历史鉴权记录

**入口**：左侧菜单 **「审计日志」**。

- **作用**：每次在「鉴权校验」中点击「发起鉴权」都会写入一条记录，此处可**分页查看**，便于审计与排查。
- **内容**：结果（允许/拒绝）、操作、匹配策略、原因、主体/资源属性、时间等。

## 三、典型使用场景示例

### 场景 A：管理员可读报表，普通用户只能读普通文档

1. **用户管理**：  
   - 用户 `admin`，主体属性 `{"role":"admin","department":"IT"}`。  
   - 用户 `user1`，主体属性 `{"role":"user","department":"HR"}`。
2. **策略配置**：  
   - 策略 1（优先级 10）：`subject.role eq admin` 且 `resource.type eq report` → **允许**。  
   - 策略 2（优先级 20）：`subject.role eq user` 且 `resource.type eq doc` → **允许**。  
   - （无其他策略时，访问 report 的 user、访问 doc 的 admin 等由默认拒绝或再补策略决定。）
3. **鉴权校验**：  
   - 选用户 `admin`，操作 `read`，资源 `{"type":"report"}` → 应**允许**（匹配策略 1）。  
   - 选用户 `user1`，操作 `read`，资源 `{"type":"report"}` → **拒绝**（无匹配策略，默认拒绝）。

### 场景 B：仅做“谁对什么做什么”的快速测试

1. 在**用户管理**中至少新增一个用户并填好主体属性。  
2. 在**策略配置**中新增一条策略，规则按需填写（如 `subject.role eq admin` 且 `resource.type eq report` → 允许）。  
3. 在**鉴权校验**中选择该用户、填写资源与操作，点击「发起鉴权」查看结果。  
4. 在**审计日志**中确认刚才的鉴权记录。

## 四、流程小结（顺序可微调）

| 顺序 | 步骤         | 说明 |
|------|--------------|------|
| 1    | 启动后端、前端 | 保证能打开管理界面并访问接口。 |
| 2    | 用户管理     | 维护“谁”，以及其主体属性 JSON。 |
| 3    | 属性管理     | （推荐）统一主体/资源/环境属性名，便于策略配置。 |
| 4    | 策略配置     | 配置允许/拒绝规则及优先级。 |
| 5    | 鉴权校验     | 选用户或手填 subject，填资源与操作，发起鉴权。 |
| 6    | 审计日志     | 查看、导出或排查历史鉴权记录。 |

属性管理可与策略配置交替进行（先写策略再补属性，或先建属性再配策略）。鉴权校验和审计日志可随时使用。

## 五、常见问题

- **鉴权结果始终为“拒绝”**：检查是否有**已启用**策略，且规则中的属性名、操作符、值与鉴权请求中的 subject/resource 一致（如 `subject.role` 对应主体 JSON 里的 `role`）。
- **新增/编辑后不生效**：策略需**启用**才会参与鉴权；修改策略或用户后，下次鉴权即使用新配置，无需重启服务。
- **请求 403**：多为 CORS。确保前端访问端口（如 5173、5174、5175）已加入后端 `application.yml` 的 `cors.allowed-origins`，并重启后端。
- **主体属性怎么写**：必须是合法 **JSON 对象**，键名与策略中的 `subject.xxx` 对应，例如策略用 `subject.role` 则主体属性里要有键 `"role"`。

如需 API 明细或规则表达式格式，请参见项目根目录的 **README.md**。
